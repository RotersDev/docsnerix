Para garantir o desempenho, a estabilidade e a alta disponibilidade da plataforma Nerix para todos os lojistas, aplicamos limites de requisição (*rate limiting*) nos endpoints das nossas APIs públicas.

---

## ⚡ Limites de Uso

Os limites variam por endpoint. Os principais:

| Endpoint | Limite |
| :--- | :--- |
| `GET /api/public/products` (Listar Produtos) | **120 requisições por minuto por API Key** |
| Requisições com API Key inválida ou ausente | **60 tentativas por minuto por IP** |

Para saber o limite exato de qualquer chamada, use os cabeçalhos abaixo: eles mostram o limite, quanto ainda resta e quando a janela reinicia.

---

## 📊 Headers de Controle

As respostas de endpoints com limite incluem cabeçalhos para você acompanhar o consumo em tempo real:

| Header | Descrição |
| :--- | :--- |
| `RateLimit-Limit` | Limite total de requisições na janela atual. |
| `RateLimit-Remaining` | Quantas requisições ainda restam antes de atingir o limite. |
| `RateLimit-Reset` | Segundos até a janela reiniciar. |

O endpoint **Listar Produtos** também envia `X-RateLimit-Limit`, `X-RateLimit-Remaining` e `X-RateLimit-Reset` (este último em Unix epoch, em segundos).

Se a sua aplicação exceder os limites, a API retornará o status **`HTTP 429 Too Many Requests`** acompanhado do cabeçalho:
*   `Retry-After`: Tempo em segundos que você precisa esperar antes de tentar fazer uma nova requisição.

---

## 💡 Boas Práticas

- **Trate erros 429:** Garanta que sua aplicação escute o status `429` e implemente uma estratégia de *backoff exponencial* (esperar antes de tentar novamente).
- **Monitore os Headers:** Use o cabeçalho `RateLimit-Remaining` para adaptar o ritmo de envio de requisições da sua aplicação.
- **Cache de Dados:** Faça cache local de requisições de leitura que mudam raramente (como listagem de categorias ou produtos).
